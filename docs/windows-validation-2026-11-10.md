# Windows 實測與修正（2026-11-10）

環境：Windows、本機安裝的 Google Chrome、專案 `.venv` 的 Python 3.12.16。原版為 `8303375`。測試桃園台茂店、2026-11-19、2 大 0 小；正式網站測試均未送出訂位，也未寄信。

## 原版實際行為

- 直接呼叫原版 `check_day`，以原設定 `channel="chrome", headless=False` 啟動，單日查詢讀到 11:30、17:30，未出現驗證，且沒有點日曆。
- 原版訂位分支另測到選桌型、選時段與摘要。診斷攔截了開啟聯絡表單的點擊，未進入表單。一般 → 板前吧台 → 11:30 → 準備開表單的操作起點間隔分別約 0.266、0.109、0.094 秒。
- `playwright-cli` 的另一個獨立 Chrome 進站即顯示「按壓不放以確認您是人類」，沒有繼續操作，也沒有嘗試自動通過驗證。

原專案流程當下沒有重現「長按後再試一次」。上述差異無法證明速度是唯一原因，也沒有以使用者平常的 Chrome 個人設定檔做對照。

## 修正

- 同一次查詢共用操作節奏，每次載入、重新整理、日曆、人數、桌型、時段及聯絡表單操作之間至少間隔 2 秒；等待期間可取消，若出現驗證就停止。
- 等待時段結果連續穩定 0.8 秒，並等待 `inline.app` 及其子網域的 fetch／XHR 完成。避免桌型已選中，但時段仍是切換前的結果。
- 已符合日期、人數的頁面直接讀取；改人數後若日期仍正確，也不重點日曆。
- 等摘要內容更新並核對分店、日期、人數、桌型、時間後才繼續。
- 首次讀取失敗時不繼續掃描其他日期；遇到驗證保留先前讀到的時段與原 Chrome。
- 新增不含個資的單調時鐘步驟紀錄，以及只查詢／只核對摘要的診斷入口。

## 23:05 使用者再次遇到驗證後的修正

使用者確認勾選「不限日期」。其 `query-20261110-230423-a01a6fcd.jsonl` 顯示程式約 50 秒內先向後翻 11 個月，再反向翻月；後來兩次日曆操作逾時，仍繼續處理下一日期。舊偵測也未標記截圖中的頁內驗證彈窗。先前單日成功不能視為已解決這個問題。

找到並修正的具體錯誤：

- 網站的「還有幾個日期可選」位於 `#book-now` 內，卻在 `#book-now-content` 外；舊定位找不到總數，便翻完整年。
- 不限日期不再強選今天，而是讀取網站已選日期；候選日期去重，不再掃完後往回翻全年。
- 日期總數缺失或遇到無新增日期的月份時，停止盲目翻月並顯示掃描不完整。
- 桌面網站同時顯示兩個月；第二個月已顯示的日期直接點選，不再多翻一頁；結果核對也支援第二個月。
- 驗證偵測新增頁內長按提示與其他 px 驗證容器，仍忽略隱藏元件和一般 reCAPTCHA。
- 查詢、掃日曆或訂位操作逾時／失敗時停止後續操作，保留畫面供檢查。
- 紀錄補上公開查詢條件、結果日期與實際失敗步驟。

本機 Chrome 回歸測試增至 18 項。正式網站以不限日期、3 大 0 小及開啟訂位分支測試，使用強制停在摘要的診斷包裝：成功讀到 2026-11-19 11:30，核對訂位摘要成功，未翻月、未開聯絡表單、未送出訂位。

緊接著另開獨立 Chrome 測試不限日期純查詢時，在首次進站便出現人機驗證；當時尚未點日曆或變更人數，程式正確識別並停止。沒有繼續重試或自動處理驗證。因此，這次修正證實了不限日期的程式錯誤已改善，**尚不能宣稱網站人機驗證問題已完全解決**。純查詢的正式網站掃描路徑本次受驗證阻擋，其日曆定位與停止行為已由模擬回歸測試核對。

## 23:20 瀏覽器會話排查

使用者確認同一電腦、同一網路下，平常 Chrome 仍可正常進入，只有程式開啟的 Chrome 遇到驗證。已確認本機 Chrome 157.0.8103.39，Playwright 1.65.0；程式指定使用已安裝的 `chrome` 通道。

程式原本每次查詢建立臨時會話，關閉後不保留 Cookie 和網站儲存。已改為查詢及診斷共用 `.browser-profile/` 專用資料夾，遵照 [Playwright 的持續會話說明](https://playwright.dev/python/docs/api/class-browsertype#browser-type-launch-persistent-context)，與日常 Chrome 個人設定檔分開。沒有新增偽裝自動化、修改指紋或自動完成驗證的行為。

19 項回歸測試通過；新增測試用攔截的本機頁面，確認關閉並重新開啟 Chrome 後，持久 Cookie 和 localStorage 都保留。

正式網站測試結果：固定會話首次查詢 2026-11-19、2 大 0 小，成功讀到 11:30；之後由實際 Tk 視窗重開同一會話，仍在載入後約 1 秒即遇到人機驗證，未進行日曆或訂位操作（`query-20261110-232034-5a06f28a.jsonl`）。因此保留 Cookie 也不足以解決。現有證據更指向網站對程式控制的瀏覽器會話之風險判定，但尚未取得網站端原因，不能斷言唯一因素或宣稱監看已可靠可用。

## 23:45 後續定位：JavaScript 調試事件訂閱可重現拒絕

以相同的 Chrome 執行檔、同一台電腦與網路，進一步分開測試普通啟動、開啟本機調試端口、Playwright 連接，以及最小 CDP 頁面控制。沒有自動操作任何人機驗證。

| 對照 | 結果 |
| --- | --- |
| 普通 Chrome，無調試端口、無 Playwright，獨立資料夾重開 | 兩次均正常顯示訂位頁，已檢查視窗截圖 |
| 普通 Chrome，開本機調試端口，但不連接 Playwright | 兩次均正常顯示訂位頁，已檢查視窗截圖 |
| 普通 Chrome，連接 Playwright（`no_defaults=True`） | 首次可用，後續重開出現 HTTP 403 與驗證頁 |
| 最小 CDP：只導航、讀取，不啟用調試事件 | 兩次啟動，各刷新一次，四次皆 HTTP 200、`blocked=false` |
| 與上一列相同，唯一新增 `Runtime.enable` | 首次載入 HTTP 200；刷新變成 HTTP 403、`blocked=true`；重開仍 HTTP 403 |

最後兩列使用相同的最小客戶端程式，只由參數控制是否送出 `Runtime.enable`，各用自己的測試資料夾。這是在本機可重現的觸發條件，足以解釋為何加延時、保留 Cookie、甚至正常啟動後再連接 Playwright都未能解決。網站端的完整風險模型仍不可見，不能據此宣稱這是其唯一檢測信號。

也在本機 Playwright 1.65.0 的 `driver/package/lib/coreBundle.js` 中確認，頁面初始化會送出 `Runtime.enable`；`no_defaults=True` 不會略過這一步。`Runtime.enable` 是訂閱 JavaScript 執行環境事件的指令，與單次 `Runtime.evaluate` 不同，參考 [Chrome DevTools Protocol Runtime](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/)。

### 實作修正

新增 `native_browser.py`，以普通 Chrome 啟動專用會話，使用官方頁面導航、DOM 讀取、輸入及網路完成事件等必要指令。移除查詢路徑對 Playwright 瀏覽器初始化的依賴，不啟用 `Runtime.enable`／`Inspector.enable`，不注入初始化腳本或改寫瀏覽器環境、指紋、驗證程式。

- 使用 `.browser-native-profile/` 專用資料夾，與先前的調試測試資料夾分開，保留原資料供排查；不讀寫日常 Chrome 個人設定檔。
- 調試端口僅綁定本機回環位址，關閉查詢時只關閉本次啟動的 Chrome。
- 保留原有查詢條件、訂位摘要核對、最多送出一次、遇到驗證停止及先前結果保留的行為。
- 新增同一組互動測試在新客戶端執行；另外核對刷新不讀舊文件、簡訊驗證表單節點身分，以及不啟用已知觸發指令。
